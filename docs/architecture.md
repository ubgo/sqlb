# How SQLB works

SQLB is a typed SQL library for Go packages that own tables and need applications to compose queries across package boundaries. Libraries export Table and Expr[T] values; callers supply joins, predicates and destinations. This avoids requiring a shared ORM model or a model generator. The cookbook boundary test keeps the example packages from importing one another. ## Modules and package boundaries

The workspace contains eight Go modules: the root plus contrib/debug, driver-mysql, driver-pgx, driver-sqlite, migrate, structbind and vet. Root packages use the standard library; external driver dependencies stay in contrib modules. go.work joins development checkouts, including its local replacement, so published module manifests need not point at local directories. [workspace](ds:block?id=workspace-f7vpgvxp) [core boundaries](ds:block?id=core-boundaries-y4kpz7kr&assert=true)

The root sqlb facade exposes expression, statement, binding and execution APIs. render owns SQLer, Args and the minimal Dialect contract. dialect/* supplies engine spelling; expr builds typed expressions; stmt owns statement structure and Query; bind couples expressions to pointers; exec uses database/sql-compatible DBTX; scan adds value readers. schema and ddl form the optional schema path, and pg/mysql/sqlite/ch hold engine constructs. Contrib modules isolate drivers and tooling from the root dependency budget. Keeping these boundaries explicit makes it possible to import or extend a lower layer without adopting the facade. [core boundaries](ds:block?id=core-boundaries-y4kpz7kr&assert=true) [typed expression](ds:block?id=typed-expression-bpqvb4a9) [dialect contract](ds:block?id=dialect-contract-smkbmeyz) [select build](ds:block?id=select-build-h68d49p3) [bound one](ds:block?id=bound-one-x39s9kka) [reader flow](ds:block?id=reader-flow-xcq2taqt) [ddl contract](ds:block?id=ddl-contract-s2xdb9he) [workspace](ds:block?id=workspace-f7vpgvxp)

The workspace module roles are: `driver-pgx`, `driver-mysql` and `driver-sqlite` for connections and engine execution tests; `migrate` for schema planning/execution; `vet` for declaration and catalogue checks; `structbind` for optional reflection-based struct mapping; `debug` for query explanation. They remain separate dependency units. [workspace](ds:block?id=workspace-f7vpgvxp)

## From typed values to rows

Expr[T] is a concrete generic expression carrying rendering behavior and optional column metadata. Col[T] declares the Go type; it does not inspect a database. Bind couples that type to a destination pointer. schema.Col adds a check against declared schema metadata, not against the live catalogue. This distinction matters because compiler success does not establish that a deployed schema matches the declaration. [typed expression](ds:block?id=typed-expression-bpqvb4a9) [column declaration](ds:block?id=column-declaration-gthk6bb2) [schema types](ds:block?id=schema-types-r4ut75bs&assert=true)

Caller-owned typed columns and predicates enter a statement builder. Build walks SQLer nodes using one Args, preserving traversal order between placeholders and argument values. Dialect spelling and engine guards run during rendering. Build collects matching binding Targets only after successful rendering. exec queries through DBTX and scans into those targets; scan instead appends Reader columns and allocates its own destinations for each row. This explains why projection order, parameter order and destination ownership are correctness invariants, rather than formatting details. [column declaration](ds:block?id=column-declaration-gthk6bb2) [select build](ds:block?id=select-build-h68d49p3) [parameter flow](ds:block?id=parameter-flow-pdh445xg) [dialect failure](ds:block?id=dialect-failure-zqdgvzs3&assert=true) [bound one](ds:block?id=bound-one-x39s9kka) [reader flow](ds:block?id=reader-flow-xcq2taqt) [reader composition](ds:block?id=reader-composition-ymehc5ss)

A select builder renders through a fresh Args, then returns Query SQL, ordered Args and scan Targets. Build returns an empty Query on rendering failure. Ordinary parameters become placeholders plus argument values, rather than SQL text. This lets callers reject build errors before executing an incomplete query; explicit raw/literal APIs remain an author-controlled boundary. [select build](ds:block?id=select-build-h68d49p3) [parameter flow](ds:block?id=parameter-flow-pdh445xg) [build failure](ds:block?id=build-failure-pwec46e6&assert=true) [bound values](ds:block?id=bound-values-3t7cnq5d&assert=true)

Binding execution writes through caller-owned Targets; exec.One checks uniqueness and exec.Each reuses destinations per row. Value readers compose columns and allocate destinations per row; scan.One returns the first row. These APIs solve different ownership needs: short per-call bindings versus reusable value readers. Reader allocation and mapping callbacks must themselves respect that ownership contract. [bound one](ds:block?id=bound-one-x39s9kka) [bound each](ds:block?id=bound-each-qvvzm6tq) [reader flow](ds:block?id=reader-flow-xcq2taqt) [reader allocation](ds:block?id=reader-allocation-nktfvyeg) [reader cardinality](ds:block?id=reader-cardinality-332zvda7&assert=true)

A bound Query contains addresses into caller state. Builder-derived queries share an execution guard so overlapping executions fail rather than write through those addresses together; independently constructed queries can still point at the same variables, so callers must preserve ownership. Custom builders should propagate NewGuardedQuery guards, not rely on a Query struct literal. Reader composition builds per-row allocators instead, allowing reuse when custom allocators and callbacks are concurrency-safe. Neither mechanism synchronizes arbitrary caller access to destination variables. ## Dialects

Postgres renders numbered $n placeholders and double-quoted identifiers. SQLite uses ? and double quotes; MySQL and ClickHouse use ? and backticks. Postgres and SQLite implement RETURNING; MySQL and ClickHouse decline it. Dialect requires Placeholder and QuoteIdent, while optional interfaces add capabilities. Small interfaces let external dialects participate without a registry change. [dialect contract](ds:block?id=dialect-contract-smkbmeyz) [dialect matrix](ds:block?id=dialect-matrix-efpaw6ht&assert=true)

| Engine | Placeholder | Identifier quotes | RETURNING | Execution evidence |
|---|---|---|---|---|
| Postgres | `$1`, `$2`, … | double quotes | supported | DSN-gated live suite; version/extension gates |
| MySQL | `?` | backticks | declined | DSN-gated MySQL 8 suite |
| SQLite | `?` | double quotes | supported | local pure-Go driver tests |
| ClickHouse | `?` | backticks | declined | rendering tests; no live driver module |

The spelling and RETURNING matrix is asserted by the [dialect test](ds:block?id=dialect-matrix-efpaw6ht&assert=true). The live-suite boundaries are visible in the [postgres gate](ds:block?id=postgres-gate-ctc94x6a), [mysql gate](ds:block?id=mysql-gate-xzbtwu8b), [sqlite pragmas](ds:block?id=sqlite-pragmas-d6qmetcs&assert=true) and [workspace](ds:block?id=workspace-f7vpgvxp). ## Schema and migrations

ddl builds authored CREATE/ALTER/DROP statements and returns a Script of Statements carrying execution flags. schema.Set assembles declarations from independent owners and orders foreign-key dependencies. contrib/migrate offers Install, Execute and a checksum ledger in addition to Plan. The caller supplies schema changes and execution timing; this is not automatic inference of a live-schema diff. [ddl contract](ds:block?id=ddl-contract-s2xdb9he) [schema sort](ds:block?id=schema-sort-wshjpc9c) [migration install](ds:block?id=migration-install-ennvmeq2) [migration execute](ds:block?id=migration-execute-hgdykxdq) [migration ledger](ds:block?id=migration-ledger-h5dv2yvb)

Install calls Describe on contributed table builders, assembles schema.Set, validates dependencies and builds tables in sorted order. Execute runs the resulting Script on a pinned connection and interprets transaction, check and conditional-execution flags. Ledger adds owner/name identities, script checksums and locking around migration execution. The separation is needed because statement rendering, dependency ordering and operational execution have different failure boundaries. MySQL implicit DDL commits mean partial migration recovery needs repeatable authored scripts. ## Invariants and testing

task check runs module formatting, vet and tests, then negative type checks, the zero-dependency gate, reuse/task/doc checks, the promise gate and frozen Docsync validation. SQLite tests execute locally. PostgreSQL and MySQL integration tests skip without SQLB_PG_DSN and SQLB_MYSQL_DSN; PostgreSQL extension availability and server version add further gates. ClickHouse has render coverage here, not a live driver suite. A green default run therefore differs from verified server execution. The central invariants are ordered parameters and destinations, refusal of known unsupported dialect constructs, explicit destination ownership, deterministic schema ordering and the root dependency boundary. Their reasons follow from the pipeline above: breaking one can return the wrong data even when the SQL is syntactically valid.
