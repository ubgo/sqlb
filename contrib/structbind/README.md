# `contrib/structbind` — columns and bindings from struct tags

```go
import "github.com/ubgo/sqlb/contrib/structbind"
```

Derives a table's column list, scan bindings and insert assignments from a struct's `db:` tags, so the list is written once instead of once per statement.

## Usage

Declare the mapping once, at package level:

```go
type account struct {
	ID    string `db:"id"`
	Email string `db:"email"`
	Age   int    `db:"age"`
}

var accounts = expr.Table{Name: "accounts", Alias: "a"}
var accountMap = structbind.MustNew[account](accounts)
```

Read into a struct:

```go
var out account
q, _ := stmt.NewSelect(d).
	Columns(accountMap.Bindings(&out)...).
	From(accounts).
	Where(expr.Eq(id, "a1")).
	Build()
exec.One(ctx, db, q)
```

Read many rows as values:

```go
rows, err := scan.All(ctx, db,
	stmt.NewSelect(d).From(accounts).Order(expr.OrderBy(id, expr.SortAsc)),
	accountMap.Reader())
// rows is []account
```

`Reader` and `Bindings` are the two halves of reading, and the difference is who owns the memory. `Bindings` point into a struct **you** keep, so a query holding them is not safe to share and reading many rows means copying the struct inside the loop; that is the right shape for `exec.One` and for a caller who wants the struct filled in place. A `Reader` allocates per row and returns values, so `scan.All` gives a `[]account` directly and one `Mapping` may be read by any number of goroutines at once — pinned under `-race` by `TestReader_SafeAcrossGoroutines`. Prefer `Reader` for reads unless you specifically want the caller-owned struct.

Write from one:

```go
in := account{ID: "a1", Email: "ada@x.com", Age: 36}
q, _ := stmt.NewInsert(d).Into(accounts).Row(accountMap.Assignments(&in)...).Build()
```

```
INSERT INTO "accounts" AS "a" ("id", "email", "age") VALUES ($1, $2, $3)
```

`Exprs` gives the same columns with no scan targets, for a subquery or a caller that scans on its own. `Columns` gives the names.

A `Mapping` does all its reflection in `New`, so it holds no mutable state and is safe to keep in a package-level variable and use from any number of goroutines. The per-statement calls take the struct they point at, which is why a `Mapping` is shared and the bindings are not.

## Column names

A field with a `db:` tag uses that tag, always. A field without one gets its name from a `Namer`, and the default is `Snake`:

```go
type user struct {
	ID        string
	CreatedAt time.Time
	IsActive  bool
}

structbind.MustNew[user](users).Columns()
// [id created_at is_active]
```

There is no universally correct convention, which is why this is a parameter. Columns named `createdAt` are ordinary in schemas generated by JavaScript-side tooling, so a fixed rule would be wrong for those schemas rather than merely inconvenient:

```go
structbind.MustNew[user](users, structbind.Camel).Columns()
// [id createdAt isActive]
```

| Namer | `CreatedAt` | `HTTPStatus` | `URLs` |
|---|---|---|---|
| `Snake` (default) | `created_at` | `http_status` | `urls` |
| `Camel` | `createdAt` | `httpStatus` | `urls` |
| `Pascal` | `CreatedAt` | `HttpStatus` | `Urls` |
| `Lower` | `createdat` | `httpstatus` | `urls` |
| `Exact` | `CreatedAt` | `HTTPStatus` | `URLs` |

Anything else is a function:

```go
structbind.MustNew[user](users, func(field string) string {
	return "col_" + strings.ToLower(field)
})
```

The `Namer` is an argument to `New`, never a setting. Handle-wide mappers put the equivalent on the shared handle as a package-level function, which makes the meaning of a struct depend on mutable state elsewhere in the process; two libraries sharing a handle then fight over it and the loser's columns are wrong at runtime with nothing to point at. Passing it here keeps one `Mapping`'s answer knowable from one call site.

### Word splitting

`Snake`, `Camel` and `Pascal` split a run of capitals as one word, so `HTTPStatus` is `http_status` rather than `h_t_t_p_status`, and a trailing lowercase `s` belongs to the run before it, so `URLs` is `urls` rather than `ur_ls`. Both rules are there because the obvious implementation produces names no database has.

There is **no list of known initialisms**, deliberately. Such a list is a decision about somebody else's vocabulary that can never be complete, and it makes the output depend on whether a word happened to be in it. The one visible consequence is that `OAuth2Token` becomes `o_auth2_token`:

```go
type token struct {
	OAuth2Token string `db:"oauth2_token"` // derivation is wrong here, so say it
}
```

That is what the tag is for, and it is exact, local, and already the documented escape hatch.

### Two fields, one column

A `Mapping` whose fields do not resolve to distinct columns is an error:

```go
type bad struct {
	ID string
	Id string
}

_, err := structbind.New[bad](users)
// structbind: two fields resolve to the same column: ID and Id both map to "id"
```

This is an error rather than last-one-wins because the failure is otherwise invisible. Two fields mapping to `id` render `SELECT "id", "id"`, which every engine accepts; both scan targets then receive the same value and one of your fields silently holds the wrong data, with no error at any layer. A `db:` tag that happens to match a name derived from another field does the same thing, and is caught the same way.

The check runs against the derived names, not the field names, so the same struct can be legal under one `Namer` and rejected under another — `ID` and `Id` are distinct under `Exact` and collide under `Snake`.

## Tag rules

| Field | Column |
|---|---|
| `Name string \`db:"name"\`` | `name` |
| `Email string` (no tag, exported) | from the `Namer`; `email` by default |
| `CreatedAt time.Time` (no tag) | `created_at` by default, `createdAt` under `Camel` |
| `Secret string \`db:"-"\`` | excluded |
| `cache int` (unexported) | excluded |
| embedded struct with no tag | its fields are contributed, so a shared base struct works |

## Errors

`New` returns an error rather than panicking, and `MustNew` is the package-level-variable form that panics because there is nobody to return it to. Every failure is detected once, in `New`, not per statement:

| Error | When |
|---|---|
| `ErrNotAStruct` | the type parameter is not a struct |
| `ErrNoColumns` | the struct has no usable fields, which would build a statement selecting nothing |
| `ErrDuplicateColumn` | two fields resolve to one column; the message names both Go fields |
| `ErrEmptyColumn` | a custom `Namer` returned `""`, which would render `"u".""` |

All four wrap with `%w`, so `errors.Is` works:

```go
if _, err := structbind.New[user](users); errors.Is(err, structbind.ErrDuplicateColumn) {
	// two fields want the same column
}
```

`ErrEmptyColumn` is only reachable through a custom `Namer`: every `Namer` in this package returns a non-empty name for a non-empty field, and a field name is never empty. It is checked anyway because the alternative renders a quoted empty identifier, which is valid SQL that no table has, so the failure would arrive from the engine pointing nowhere near the cause.

The struct tag this package reads is `structbind.TagKey`, which is `"db"` — the convention most Go database packages use, so a struct already annotated for one of them works here unchanged.

## The cost

This is stated plainly because it is the whole trade.

Column names come from struct tags or from a `Namer`, so **a typo in a tag, or a convention that does not match the schema, is a runtime error** where a typo in an `expr.Col` declaration is a compile error. And the Go type of a field is **never checked** against the column's: a `string` field mapped to an integer column builds a perfectly good statement and fails at the scan.

That is exactly the checking `sqlb` exists to provide, and this package gives it up in exchange for not writing the list.

**Code generation over [`schema`](../../docs/schema/README.md) is the better answer** where a schema exists: a generator can emit the `Col` declarations *and* the bindings, giving the same convenience with the checking intact. That is the design's intended path. This package is for the case where no schema declaration exists and the list is the thing you want gone.

## Why this package can exist at all

`bind.Bind` takes an `Expr[T]` and a `*T`. Reflection has no static `T` to give it, so a reflection-driven binder cannot use it.

It works because `stmt.Binding` is an **interface** with three methods and nothing unexported:

```go
type Binding interface {
	SQL(a *Args) string
	Target() any
	ColumnName() string
}
```

So this package implements it, from outside the module, and its bindings go straight into `Columns` alongside ones built by `bind.Bind`.

That is worth saying because it is the claim the architecture makes: a community package can supply its own result strategy. This package is the test of it. If `Binding` were ever turned back into a struct, `structbind` would become impossible, and `TestMapping_ImplementsStmtBinding` is what would say so.
