# AGENTS.md

Instructions for AI agents working in this repository. Humans should read [CONTRIBUTING.md](./CONTRIBUTING.md), which says the same things in the same order.

## What this is

A typed SQL layer for Go libraries that own database tables and cannot depend on an ORM. Start with [docs/engines.md](./docs/engines.md) for engine support and execution limits, then [docs/README.md](./docs/README.md) for the topic index. The private `docsi/` workspace is optional and is not part of a public clone.

## Before you finish

```sh
task check
```

Every module formatted, vetted and tested, then the type-check, zero-dependency, reuse, task, documentation, promise and Docsync gates. If it is not green, the change is not done.

## Rules that override your defaults

**Never suppress a diagnostic to make a gate pass.** No `//nolint`, no deleted assertion, no skipped test, no loosened type. Fix the cause. A suppressed error is a defect, not a fix.

**Zero third-party dependencies in the root module.** If a change needs one, it belongs in a contrib module. `task zerodep` enforces it.

**Only universal SQL in the core.** A construct goes in the core only when Postgres, MySQL 8, SQLite and ClickHouse all accept it with the same syntax and meaning. When one differs, it goes in the engine package, even if the other three agree. Check all four before adding anything to `constants.go` or the core. Postgres, MySQL and SQLite have dialects and execution suites. ClickHouse rendering is covered, but server execution remains unverified.

**Every engine construct is guarded and tested.** Use the constructors `pg` exports, pass the construct name, and add the case to the package's guard test.

**Never edit `pg` to add an extension.** Copy `pg/postgis`. The four steps are in [docs/extensions.md](./docs/extensions.md).

**Every export gets its own doc comment**, saying why it exists and what stays true. A comment above a group documents only the first symbol.

**Do not add scope nobody asked for.** No helper because the other engines have one, no dialect without a consumer, no abstraction for a second caller that does not exist.

## Where things live

| Path | What goes there |
|---|---|
| `/*.go` | the core, zero dependencies, universal SQL only |
| `pg/`, `ch/` | one engine's constructs |
| `pg/<ext>/` | one Postgres extension each |
| `sqlbtest/` | the conformance suite; a new execution guarantee becomes a case here |
| `contrib/<role>-<name>/` | a separate module, for anything needing a dependency |
| `examples/` | catalogues whose SQL is checked by `go test` |
| `docs/` | one document per topic |

## Verification, not assertion

A claim in a comment or a README is not verified; only the build and the tests verify it. A rendering claim needs an example with its expected SQL. An execution claim needs a conformance case. A type-safety claim needs a line in `examples/typecheck/bad.go` that must not compile.

## CI

`ci.yml` and `release.yml` are generated by `volt gen`; regenerate them, never edit them. `ci.yml` runs `volt ci` (format, vet, lint and race tests of the changed modules) on manual dispatch only; `release.yml` is manual and republishes an existing tag. `test.yml` and `lint.yml` stay `workflow_dispatch` only. `task check` is the gate, because it also runs the type-check, zero-dependency and documentation gates that `volt ci` does not.

# docsync rules for an AI writer and reviewer

The tool knows which sentence depends on which block and whether the block changed. Read only what `check` lists; acks are recorded against the hash.

Writing:
1. Never cite a path and line. `ds def <file>#<symbol>` for the block, then `ds:block?id=…`.
2. Never paste code. Write a `ds:block` directive; the build renders it.
3. Never type a fact. Run `ds facts`; cite with `ds:cfg` if it exists; otherwise define once with an inline `ds:def`, then cite.
4. External links go through `ds:url`. Behaviour claims cite the test with `assert=true` when one exists.
5. Add `covers` for every id a new page introduces.
6. Start a session with `ds map`. When editing a page, start from `ds context <doc> --budget N --since ack`; nothing outside it needs rereading. Use `find`, `read`, `locate` instead of grep and file reads.
7. Run `ds check` before declaring done. Run `ds impact --staged` before proposing a code change that touches defined blocks.
8. After a code change, `ds check --json` is the complete work list.
9. Before deleting or renaming code, `ds why <id>`, and handle dependents in the same change.

Reviewing:
1. `ds check --json` is the whole list; run `ds triage` first.
2. For each `unacked`, read the sentence, the class, and the diff. Still true: `ack --note`. Not true: edit, then `ack --note`. Never ack a page wholesale.
3. For each `broken`, decide from the diff whether the block was deleted or moved without its def; re-add the def or rewrite and remove the reference.
4. Produce the patch and stop; a person or an explicitly delegated agent records acks (`ack --agent --delegated-by <human>`, a person listed in `[owners]`).
5. Leave anything needing a human unacked and say why.

## Shared knowledge and documentation

Read `.lore/LORE.md` explicitly at session start (Codex does not expand Claude imports), load the Lore and Docsync skills, run `lore search "<task keywords>"`, and run `ds map --budget 2000`. Capture repository rules and decisions through Lore, then run `task lore:render`; commit `.lore/data/` with the change, keeping SQLite databases, backups and caches local. A fresh clone hydrates its local database from the shared JSON on its first Lore command.

Writing a promise into documentation means listing it in `testdata/promises.txt` and writing or updating the test that asserts it in the same change. Tag that test with `promise:<id>`. Contributor advice and historical context use `prose: <specific reason>`; software behavior requires a test. `task check` runs the promise and Docsync gates. Docsync acknowledgements remain with a reviewer or an explicitly delegated agent. See [docs/knowledge-workflow.md](./docs/knowledge-workflow.md).
